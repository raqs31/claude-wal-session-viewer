## Goal

A session that was trashed and then restored can be picked and shown again without a reload, from any tab; `drop` marks the moved ids gone; a `wal.pick` key removed by another tab empties this tab's stored pick too.

## Non-goals

- No Trash tab, useTrash or Sidebar change (T27). No change to the server or to `effective`/`prune` semantics beyond what the gone bookkeeping needs.
- No reload-based workaround, no same-tab-only `revive(ids)` callback from TrashTab (the reviewer's minimal alternative was not chosen).

## Context

Source: T19 review, major finding 1 and minor follow-up 3; board Decision 2026-10-22 "[auto] T19 pick fix: use the reviewer's cross-tab design ... also honour wal.pick key removal from other tabs".

Bug (T19, reproduced): on a trash the server notifies every usage stream on the moved ids with `unknown=[ids]` (scripts/wal-server.ts:125-135); App.tsx:49 calls `forget(usage.unknown)`; `gone` (web/src/usePick.ts:22) only ever grows (`forget` :65). After a restore the ids stay gone: a click stores `wal.pick=[id]` but `prune` drops it, the fallback `newest()` skips every gone id, and with every listed id gone `effective()` returns `[]` = all sessions. `effective([A],[A,B],gone=[A,B],null)` → `[]`; with gone=[] → `[A]`.

Design (binding):
1. `forget(ids)` stamps each id with `Date.now()` (gone becomes id → stamp; re-forgetting an id refreshes its stamp).
2. `useSessions` (web/src/useSessions.ts:7, `refresh` :12) records the time each request started (`Date.now()` before `fetch`) and keeps it with the list it stored; expose it (e.g. `listedAt: number | null`) from the hook. App.tsx:44 passes it to `usePick` next to `rows`.
3. In usePick's effect (web/src/usePick.ts:53), an id leaves `gone` when the current list was requested after that id's stamp and lists it. Put this rule in a pure helper in web/src/lib/pick.ts (beside `effective` :26) and call it from usePick; keep handing `effective`/`prune` a `readonly string[]` of gone ids.
4. `drop(ids)` (:74) also adds the moved ids to gone, stamped now, so the emptied-pick fallback cannot land on a moved id still in the pre-refresh list. Keep its current shownRef and key-removal behaviour (board Decisions on T17 drop).
5. The storage handler (:44-51) calls `adopt(null)` when `e.key === KEY && e.newValue === null`; other keys and parse failures stay ignored as now.

Tests in web/src/lib/pick.test.ts (copy the style of :34), one assertion each for the helper: an id listed by a list requested after its stamp leaves gone; an id listed by a list requested before (or at) its stamp stays; an id not listed stays; ids not in gone are untouched. Plus one `effective` case: after the revival, `effective([A],[A,B],gone=[],null)` → `[A]` (the T19 repro).

Playwright MCP (mcp__playwright__browser_*), never the real ~/.claude: `npm run build`; `TMP=$(mktemp -d)`; copy `scripts/fixtures/projects/` to `$TMP/.claude/projects/`; make most sessions idle (WAL ending in `SessionEnd` or none, mtime > 2 min old via `touch -d`), one live; start `HOME=$TMP node scripts/wal-server.ts --port=0` in the background, note its PID, URL from its `wal viewer: http://…` line. Decisions:
- gone held as a Map id→stamp; the effect revives and returns early, re-running with the new map, so effective/prune get only `string[]`.
- revive treats a list requested at exactly the stamp as stale (strict `<`), as the ticket's "before (or at)" test asks.
- forget([]) is a no-op so App's usage effect does not churn state on every empty `unknown`.

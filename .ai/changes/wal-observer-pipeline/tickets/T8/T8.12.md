Source: T9 finding [major] and T9 follow-up 2 in the T8 Comments.

- A: `scripts/wal-server.ts:365` seeds `stale` from the open-time `pipe` (from `syncAll` at `:341`). A target that turned stale after the first page, but before the stream opened, is then never announced. Fix: `const client: Client = { res, ixs, hit: matcher(p), pos, gens, stale: new Set() }` (`:366`); delete the `:365` line. The tick (`:176-180`) then sends `event: stale` once per stream for each stale session. A repeated stale frame is idempotent for the page.
- Fix the comment at `:60`: the set holds picked ids this stream already sent an `event: stale` for. It no longer mentions the first page.
- C: the comments at `:377` ("catching a truncation ... before `off` points at new bytes") and `:421` ("a shrink since the last tick bumps gen here") describe the old reset. Now a shrink freezes the target with the same gen, and the rows keep their bytes. Rewrite both to say what the sync before the read does now, one line each. Read `:169` too and fix it only if it also claims a gen bump on a shrink.
- Test, in `scripts/live-tail.test.ts`, next to the race case (`:290-302`); copy its pattern and use `session`/`trio` (`:253`, `:260`), `events`, `open`, `after`, `until`, `wait`, `staleOf`, `check`:

  3. `stream = await open(after(page, 'ids=<id>'))`, the original first page's vector, as a reconnect reuses it; `await wait(600)`.
  4. One check: `stream.stale.join() === staleOf(id, 'wal shrank') && stream.resets === 0`.
- Existing stale checks (`:275-335`) must still pass unchanged: each stream gets exactly one stale frame.

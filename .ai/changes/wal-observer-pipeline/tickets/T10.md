## Goal

The server takes the cache lock, runs a background loop that builds the backlog and follows every session, reports progress at `GET /observer` and rebuilds on `POST /rebuild` (plan.md Phase 5 §1, §2). Add `scripts/observer-server.test.ts` with the server cases of Phase 5 §4. Export from `scripts/observer.ts` a rebuild function that T11 (CLI) reuses.

## Non-goals

- No CLI and no README change (T11).
- No web UI for the chip or Rebuild (Phase 8).
- No automatic rebuild: a rebuild is manual only.

## Context

Plan: `.ai/changes/wal-observer-pipeline/plan.md`, Phase 5 and "Single writer".

Build on T8 (server reads targets via `observer.sync`) and T1 (`acquireLock(dir)` / `releaseLock` in `scripts/target.ts`).

Contract (copied from plan.md Phase 5):
- At start, the server takes the lock of each source's target dir. With the lock, it runs a 1 s loop over all `discovery.list()` sessions (`scripts/discovery.ts:373`). Each tick works in slices of at most 50 ms, so requests stay fast.
- `sync` reports `done` / `total` as WAL plus transcript bytes.
- New sessions and grown sources are synced. Sessions never built are built in the background.
- Without the lock, the observer is not started (read-only mode), and the server logs that once. Read-only still serves the targets.
- `GET /observer` reports the progress. `POST /rebuild {ids}` deletes those targets and the in-memory state; the loop then builds them again. It uses the existing `crossSite` (`scripts/wal-server.ts:220`) and `writeOf` (`:239`) POST pattern.
- `shared/api.ts`: `ObserverStatus = {owner: boolean; total: number; built: number; building: string[]; stale: {id, reason}[]}`. `/rebuild` returns `{results: {id, ok, error?}[]}`. It is refused with 409 in read-only mode.

Security: `ids` come from the page. Validate every id with `validId` (`scripts/sessions.ts:18`) and build target paths only through `targetPath`, as `/trash` does (`scripts/wal-server.ts:243`). A cross-site POST is refused like the trash routes.

Tests (server cases of plan.md Phase 5 §4), through `startServer` (`scripts/test-server.ts:13`) with a temp `HOME`: the backlog builds with no request and `/observer` reaches `built === total`; a WAL appended with no client open is synced by the loop; a shrunk WAL appears in `stale` and its rows stop updating; `/rebuild` clears the stale state and rebuilds; a second server is read-only and refuses `/rebuild` with 409.

Do not commit; the orchestrator commits each phase after its review.

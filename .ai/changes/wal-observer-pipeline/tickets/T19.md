Decisions:
- Patches go for every tok's target, whatever the stream's filter, as the contract says. The page ignores a seq it does not hold.
- A target at or after this tick's start pos is not sent again as a held row: the scan above already judged it with its final numbers. It still gets a patch, which repeats the numbers in its row frame.
- The held check runs the bare row (out and res null) first, so with a token filter the matcher rejects it before the q disk read.
- A tick with only patches sends no row frame, so Last-Event-ID stays before the tok and a reconnect replays the patch. That is harmless, since a patch is idempotent.
- No token-filter flag on Client: without a token filter, bare and numbered rows match alike, so no held row is sent.

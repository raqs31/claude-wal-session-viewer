## Goal

Add `scripts/observer.ts`: per session it reads the WAL from the checkpoint and appends `head`, `ev`, `call` and `ck` records to the target, resumes after a restart and freezes a changed source (plan.md Phase 2 §1). Add `scripts/observer.test.ts` with the Phase 2 §2 cases.

## Context

Plan: `.ai/changes/wal-observer-pipeline/plan.md`, read "Implementation Approach" steps 1-2, "Critical Implementation Details" (Torn tail, Replay must not write) and Phase 2.

Contract (copied from plan.md Phase 2 §1):
- `createObserver({discovery, write: boolean})` gives `sync(id, budgetMs)` → `{done, total, stale}`, where done / total are WAL bytes. It also gives `state(id)` and `drop(id)`.
- The per-line derivation comes from `indexLine` (`scripts/wal-index.ts:129`): `t`, event, cat, tool, `dur`, `tuid`, agent, agentType, mcp, err. An unparseable line takes the previous `t`, else the time of the pass, and the observer persists it. `day` / `minute` are not stored (they depend on the server time zone).
- `ev` holds the derived fields, the WAL byte offset `woff`, and `rec` (parsed WAL record) as last key; unparseable lines hold `raw` instead.
- `call`: one per tool call, written when its Post / PostFailure is read: `tuid`, `t` (Pre `ts`, else Post `ts`), `end` (Post `ts`), `dur`, `tool`, `mcp`, `err`, `agent`, `agentType`, `input` and `response` (`tool_response`, else `error`), `input` then `response` last.
- The open-Pre map has the same cap as `pending` today (`PENDING_MAX = 10_000`, `scripts/wal-index.ts:12`). A Post with no Pre gives a call row with `t = end`. A second Post for the same `tuid` gives no second call row.
- Restart: read the target, take the last `ck`, replay the WAL to `ck.wal.off` without writing, then continue.
- Stale: a WAL smaller than `ck.wal.off`, a new inode, or a `head.v` other than `TARGET_VERSION` appends `stale {reason}` once and stops all writes for that target.
- A WAL that does not exist (for example, in trash) is skipped; that does not make the target stale.
- The WAL path is `<dir>/<id>.wal.jsonl` beside the transcript (`scripts/discovery.ts:323`); get the session through `discovery.locate`.

Tests (plan.md Phase 2 §2), over temp WALs: `ev` fields match today's `IndexEntry` for the same lines; a call row for a plain tool, an MCP tool and a failure; Post with no Pre; a duplicate Post; unparseable lines keep `raw` and a persisted `t`; resume in a new observer instance writes no duplicates; shrink and new inode give `stale` and no further writes; a torn target tail; a budget of 0 ms makes partial progress and later passes finish.

Do not commit; the orchestrator commits each phase after its review.

Decisions:
- `discovery` is typed `Pick<Discovery, 'locate'>`; the target path is `targetPath({label: '', projectsDir: dirname(dir)}, id)` (targetDir reads only projectsDir, and dir = projectsDir/slug).
- `write: false` never appends: each sync re-reads the target incrementally and reports done = last ck.wal.off, total = WAL size, stale from the target. A target reset restarts its state with the same reader.
- Replay is part of the budgeted pass: lines below ck.wal.off update the open-Pre map only and write nothing. `done` = max(read offset, ck.wal.off).
- Crash between records and ck: `ev`s after the last ck are kept in a woff→t map and not written again (their persisted t is reused); call tuids already in the target are loaded into `called` by absorb, and replayed lines no longer touch it.
- The first line after the replay takes the last persisted ev `t` before the ck as its fallback.
- call: dur = the Post's duration_ms; input = Pre tool_input, else the Post's tool_input, else null; response = tool_response ?? error ?? null; err = PostToolUseFailure for any tool.
- ev.event is null for a missing or non-string event; tool / tuid / agent / agentType are null unless non-empty strings.
- Stale reasons: `wal shrank`, `wal replaced`, `format version <v>`. A stale record is appended once.
- Follow-up 1: a target with no head holds nothing built from the old WAL, so a replaced or shrunk WAL resets the in-memory state and builds from the new file.
- Follow-up 3: the called set uses the open-Pre cap (10 000). Trade-off: a duplicate Post more than 10 000 calls after the first one gives a second row.
- Follow-up 4: the ENOENT race has no test; it cannot be timed in a test.
- Follow-up 5 is checked by behaviour only (the reset case in the write:false test).
- head is written with the first records of the first pass that has any; an empty WAL writes nothing.
- On an append error the in-memory state is dropped, so the next sync re-opens from what reached the disk.
